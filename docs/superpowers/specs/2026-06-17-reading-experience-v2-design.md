# Reading Experience v2 — Design Spec

**Date:** 2026-06-17
**Status:** Approved (pending written-spec review)
**Scope:** Improve the *reading experience* of the static macro-brief dashboard by
adding three groups of features chosen by the user: (1) faster skim, (2) what's
new / hot, (3) trader "by-asset" view. Comfort/typography (group 4) is explicitly
out of scope.

## Goals

- Let a daily reader grasp the day in ~10 seconds before drilling in.
- Make the most important story *look* most important.
- Make repeat visits show what changed since last time.
- Let a trader pivot the same stories around the assets they care about.

## Non-goals (out of scope)

- Density/compact toggle, typography pass, star/read-later (group 4).
- Any backend, accounts, or server state. All personalization is client-side
  (`localStorage`), consistent with the static-generation architecture.
- Changing the ingest/summarize/cluster logic. We only *add* one daily digest call.

## Architecture overview

The system stays: **Python renders static HTML per day** (`src/render.py` +
Jinja templates) and **vanilla JS** (`static/app.js`) adds interactivity in the
browser. No new dependencies, no backend.

Data already stored per story is reused wherever possible: `headline`, `bullets`,
`topic`, `sentiment`, `importance`, `instruments[]`, `source`, `url`, `published`,
cluster `size`. Two new data attributes are added to each card for the JS
features. One new pipeline step produces the daily "mood" sentence.

Split of work (7 features):

| # | Feature | Group | Where it lives | Pipeline risk |
|---|---------|-------|----------------|---------------|
| 1 | TL;DR hero (mood + top 5) | skim | template + new `digest` step | low (1 call/day, fails soft) |
| 2 | Lead-story card | skim | template + CSS | none |
| 3 | "New since last visit" | new/hot | `app.js` (localStorage) | none |
| 4 | Most-covered 🔥 badge | new/hot | template (uses `size`) | none |
| 5 | Per-topic sentiment bar | new/hot | template (uses `sentiment`) | none |
| 6 | By-asset view toggle | trader | `app.js` (uses `instruments`) | none |
| 7 | Pin assets | trader | `app.js` (localStorage) | none |

Six of seven are frontend-only and cannot break the daily run. Only #1 touches
Python, and it degrades gracefully (see Failure handling).

## Feature detail

### 1. TL;DR hero — "Today in 30 seconds"
A panel above the tabs, rendered server-side for every day page.

- **Top 5:** the 5 clusters with the highest `(max_importance, size)` for that
  day, shown as a numbered list with the importance dots and source count. Each
  item links (anchor) to the full card below. Purely mechanical — no LLM.
- **Mood line:** one ≤140-char sentence summarizing the day's macro tone,
  generated by **one LLM call per day** (see digest step). Shown above the top 5.
- If no mood is available for that day, the panel renders the top 5 only (no
  empty space, no error).

### 2. Lead-story card
The single highest-priority cluster of the day — `max(max_importance, then size)`
— renders as a full-width "lead" card at the top of the stage in the **All**
view, visually heavier (larger headline, accent border). In a single-topic tab,
the lead treatment is not applied (keeps tab panes uniform). Pure template + CSS.

### 3. "New since last visit"
- Each card carries `data-ts` = ISO timestamp of `published || fetched_at`.
- On load, `app.js` reads `lastVisit` from `localStorage`; any card with
  `data-ts > lastVisit` gets a `NEW` dot. A header chip shows `"N new since
  <time>"` and a toggle filters to new-only.
- After render, `lastVisit` is updated to now (so the *next* visit is the
  reference). First-ever visit marks nothing new (no noise).
- Per-day: the reference is stored per day key so opening an old archive day
  doesn't mark everything new.

### 4. Most-covered 🔥 badge
The cluster with the largest `size` (most outlets) for the day gets a 🔥 marker
and a `most-covered` label. Uses data already computed in `_build_cluster`.
Template-only.

### 5. Per-topic sentiment bar
For each topic group, render a thin two-tone bar (bullish vs bearish share, with
neutral/mixed as muted) next to the pane title and optionally in the tab. Counts
are computed at render time from the group's clusters (extends the existing
`_tally` to per-topic). Template + CSS.

### 6. By-asset view toggle
A header control: **[ By topic | By asset ]**.

- Each card gains `data-instruments="WTI,Brent,DXY"` (comma-joined, uppercased).
- "By topic" = current behavior (panes by topic).
- "By asset" = `app.js` hides the topic panes and rebuilds the visible set
  grouped by instrument: one section per instrument that appears, each listing
  the cards that mention it (a card can appear under multiple assets). Cards with
  no instrument fall under an "Unclassified" section at the end.
- Implementation: JS clones/reorders existing card nodes into asset sections in a
  separate container; toggling back restores the topic layout. No data refetch.
- Search and "new" filters still apply in by-asset view.

### 7. Pin assets
- Clicking an instrument chip/symbol on a card toggles it pinned
  (`localStorage: pinnedAssets[]`).
- Pinned assets show a ★ and, in **By asset** view, their sections float to the
  top. A header "★ Pinned" quick-filter shows only cards touching a pinned asset.
- Pure frontend; persists across visits.

## Pipeline change: the digest step

New module `src/digest.py`, called from `src/pipeline.py` after
`summarize_pending` and before `render_site`.

- New table `digests(day TEXT PRIMARY KEY, mood TEXT, generated_at TEXT)`.
- For the **most recent day** only: if no row exists for that day, gather the top
  ~10 stories `(headline, importance, sentiment, instruments)`, send one LLM call
  via the existing `summarize.py` chain (same provider fallback) with a prompt
  that returns a single ≤140-char macro-mood sentence as JSON `{"mood": "..."}`.
  Store it. If a row already exists for the day, skip (so reruns cost nothing).
- `render.py` looks up `digests[day]` when rendering each day page; passes `mood`
  (or `None`) plus the mechanically-computed top-5 into the template.

This is **one LLM call per day**, reusing existing keys/retry/fallback. No new
secrets, no new dependency.

## Data flow

```
ingest → summarize → [NEW] digest(latest day → mood → digests table)
        → render (reads stories + digests, bakes TL;DR/lead/badges/data-attrs into HTML)
        → deploy
browser: app.js reads localStorage (lastVisit, pinnedAssets) + data attrs
         → NEW dots, by-asset regroup, pins, filters
```

## Failure handling

- **Digest LLM fails / no key:** `digests` row not written; template renders top 5
  without a mood line. The daily run is unaffected (digest is wrapped so it can
  never raise into the pipeline).
- **localStorage unavailable / disabled:** "new" markers and pins silently no-op;
  the page still reads fine (same defensive `try/catch` pattern already in
  `app.js`).
- **A card with no instruments in by-asset view:** lands in "Unclassified".
- **Old archive days:** show top-5 (no mood, since digest only runs for latest);
  "new" reference is per-day so archives don't flood with NEW.

## Testing approach

- **Render (`python -m src.pipeline --render-only`):** verify each day page
  contains the TL;DR block, a lead card, `data-ts` and `data-instruments` on
  cards, the 🔥 badge, and per-topic sentiment bars. No template crash.
- **Digest unit:** with a stubbed LLM, assert a `digests` row is written for the
  latest day and skipped on rerun; assert pipeline continues when the call raises.
- **JS (manual against rendered site):** toggle By topic/By asset, confirm cards
  regroup and search still filters; pin an asset and reload (persists); simulate a
  prior `lastVisit` and confirm NEW dots + counter; confirm first visit marks
  nothing.
- **Cloudflare sanity:** file count still tiny; no new external requests.

## Rollout

Frontend-only features (2–7) can ship first and independently (low risk). The
digest step (1) ships with them but is guarded so a failure never affects the
existing daily brief. No change to the durable-DB or deploy steps.
